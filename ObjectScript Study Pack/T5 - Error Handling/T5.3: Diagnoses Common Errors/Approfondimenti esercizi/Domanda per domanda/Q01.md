# T5.3 · Q01 — Autorizzazione al database

[Tutte le domande](README.md) · [Approfondimenti del capitolo](../README.md) · [Domanda originale](<../../quiz.md#question-1-single>)

## Il passaggio che risolve l’esercizio

Il percorso nel PROTECT orienta la diagnosi verso la risorsa del database nel contesto del cambio namespace.

## Che cosa insegna in più

Non confondere permessi SQL sulla tabella, permessi della risorsa e stato del database. Un conflitto di lock non si diagnostica dal nome PROTECT; anche i timeout di lock hanno il loro protocollo.

## Prova a cambiare il caso

Concedere UPDATE SQL risolve sempre la mancanza di accesso al database?

<details>
<summary>Ragionamento e risposta</summary>

No.

</details>

## Testo dell’esercizio

```text
A background task running using the BackgroundDev role calls:

zn "STORE-BASE"
set obj = ##class(Sample.Customer).%OpenId(123)
set obj.City = "Ulaanbaatar"
set sc = obj.%Save()

The code terminates with a <PROTECT> error:

ZN "STORE-BASE"
^
 */db/iris/mgr/STOREBASE-DATA/

Which explanation best describes why?
```

[Apri il quiz con tutte le opzioni](<../../quiz.md#question-1-single>).

<details>
<summary>Risposta e spiegazione originali della fonte (inglese)</summary>

**Correct answer: E.** BackgroundDev does not have permission to access the database underpinning the STORE-BASE namespace

The \<PROTECT\> error with the database path shown indicates a security protection violation at the database level. The BackgroundDev role lacks the required resource permission (Read/Write) on the STOREBASE-DATA database. SQL UPDATE privileges are separate from database-level resource permissions. Lock conflicts produce \<LOCKTAB\>, not \<PROTECT\>. This matches InterSystems practice question Q23. (Reference: [Reference](https://docs.intersystems.com/irislatest/csp/docbook/DocBook.UI.Page.cls?KEY=RCOS_errors))

</details>
