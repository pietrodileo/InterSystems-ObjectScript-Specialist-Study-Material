# T3.5 · Q07 — Purge non sempre necessario

[Tutte le domande](README.md) · [Approfondimenti del capitolo](../README.md) · [Domanda originale](<../../quiz.md#question-7-single>)

## Il passaggio che risolve l’esercizio

La risposta della fonte sui vecchi piani va letta insieme al comportamento documentato di TUNE TABLE, che può ricompilare le query dipendenti quando le statistiche cambiano.

## Che cosa insegna in più

Se manca un miglioramento, verifica statistiche effettive, piano congelato, indice disponibile e collo di bottiglia: non diagnosticare automaticamente cache vecchia.

## Prova a cambiare il caso

Raccogliere statistiche identiche garantisce un piano diverso dopo purge?

<details>
<summary>Ragionamento e risposta</summary>

No.

</details>

## Testo dell’esercizio

```text
A developer runs the equivalent of TUNE TABLE from ObjectScript:

set sc = $SYSTEM.SQL.Stats.Table.GatherTableStats("Sample.Person")

After running this, they notice no improvement in query performance. What is the most likely reason?
```

[Apri il quiz con tutte le opzioni](<../../quiz.md#question-7-single>).

<details>
<summary>Risposta e spiegazione originali della fonte (inglese)</summary>

**Correct answer: B.** Existing cached query plans still use the old statistics; they must be purged

Gathering new statistics updates the metadata, but existing cached query plans were compiled with the old statistics. These cached plans continue to be used until purged. After gathering statistics, run $SYSTEM.SQL.Purge() to force new plans to be generated using the updated statistics. Statistics take effect immediately for new query compilations, no restart needed. (Reference: [Reference](https://docs.intersystems.com/irislatest/csp/docbook/DocBook.UI.Page.cls?KEY=GSQL_options))

</details>
