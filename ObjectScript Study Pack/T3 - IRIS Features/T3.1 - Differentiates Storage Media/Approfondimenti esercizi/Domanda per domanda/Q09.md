# T3.1 · Q09 — Failover e database replicato

[Tutte le domande](README.md) · [Approfondimenti del capitolo](../README.md) · [Domanda originale](<../../quiz.md#question-9-single>)

## Il passaggio che risolve l’esercizio

La domanda presuppone che PatientQueue sia in un database mirrored e che il dato confermato sia disponibile secondo quel contesto.

## Che cosa insegna in più

Un nome di global non certifica mirroring o disponibilità dopo failover: considera database, configurazione e stato della replica. IRISTEMP non è una coda di recupero.

## Prova a cambiare il caso

Spostando PatientQueue in uno storage temporaneo manterresti la stessa garanzia?

<details>
<summary>Ragionamento e risposta</summary>

No.

</details>

## Testo dell’esercizio

```text
Consider the following mirror failover scenario. Before failover, Process X on the primary member executes:

set ^PatientQueue(1) = "John Smith"
set ^||tempCalc = 42
set ^IRIS.Temp.staging(1) = "staged"

After failover to the backup member, which data is available?
```

[Apri il quiz con tutte le opzioni](<../../quiz.md#question-9-single>).

<details>
<summary>Risposta e spiegazione originali della fonte (inglese)</summary>

**Correct answer: B.** Only ^PatientQueue(1) is available because it was journaled and replicated via mirroring

Mirroring replicates journal data. Only persistent globals in mirrored databases are journaled and replicated. ^PatientQueue(1) is a persistent global that was journaled. ^\|\|tempCalc (PPG) and ^IRIS.Temp.staging (temporary global) are stored in IRISTEMP, which is not journaled and not replicated. (Reference: [Reference](https://docs.intersystems.com/irislatest/csp/docbook/DocBook.UI.Page.cls?KEY=GHA_mirror))

</details>
