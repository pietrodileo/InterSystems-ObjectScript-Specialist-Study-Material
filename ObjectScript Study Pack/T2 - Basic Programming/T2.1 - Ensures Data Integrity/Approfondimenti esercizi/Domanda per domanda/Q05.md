# T2.1 · Q05 — Proteggere il record intero per convenzione

[Tutte le domande](README.md) · [Approfondimenti del capitolo](../README.md) · [Domanda originale](<../../quiz.md#question-5-single>)

## Il passaggio che risolve l’esercizio

Il SET del telefono può riuscire perché il processo B non richiede il lock che A sta usando.

## Che cosa insegna in più

La granularità logica del lock non rende obbligatoria la convenzione: ragiona sia sul nome bloccato sia sui chiamanti che lo rispettano.

## Prova a cambiare il caso

Rinominare il lock da Patient a PatientLock obbliga gli altri SET ad aspettare?

<details>
<summary>Ragionamento e risposta</summary>

No: occorre che gli altri processi chiedano il lock concordato.

</details>

Visual connection: Core mechanisms, panel 2. See the [English diagrams and panel explanations](../tavole-esercizi.md).

## Testo dell’esercizio

```text
Process A executes:

LOCK +^Patient(42)
SET ^Patient(42,"name") = "Smith"
; ... still working ...

Meanwhile, Process B executes:

SET ^Patient(42,"phone") = "555-0199"

What happens when Process B executes its SET command?
```

[Apri il quiz con tutte le opzioni](<../../quiz.md#question-5-single>).

<details>
<summary>Risposta e spiegazione originali della fonte (inglese)</summary>

**Correct answer: C.** Process B successfully sets ^Patient(42,"phone") because it did not attempt to acquire a lock

Locks in IRIS are advisory. Process B never attempted to LOCK ^Patient(42), so there is no lock conflict. Process B's SET executes immediately and successfully. Only processes that also call LOCK ^Patient(42) would be blocked. This is why all processes must cooperate by acquiring locks before accessing shared data. (Reference: [Reference](https://docs.intersystems.com/irislatest/csp/docbook/DocBook.UI.Page.cls?KEY=GCOS_locktable))

</details>
